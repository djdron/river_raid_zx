# River Raid on the ZX Spectrum Next — notes

English | [Русский](NOTES.ru.md)

How the port is done and what was found on the way, with numbers. Addresses like A205 are the original's code; $xxxx in the Z80's address space unless said otherwise. The C++ port's files are in `deps/river_raid/port/src`.

## Memory
| Z80 | 8K page | What |
|---|---|---|
| $0000–$3FFF | 30, 31 | the Atari's RAM, at the original's addresses (state, $0500 slots, $0600–$09FF character sets, $0B00–$0FFF player-missile memory, $1000 panel, $2000–$2EFF and $3000–$3EFF screen memory, $3F04 the top line's address, $3FB3 the scrolling line's text) |
| $4000–$5FFF | 18–27 / 10, 11 / 7 | a window: Layer 2 (render_line, clearing), bank 5 (tilemap, panel_frame), page 7 (pattern cache, build_sprites) |
| $6000–$7FFF | 12 | scan_* per scanline, double_hi/lo, ch_bits, ring_lo/hi, sprite_list, ds_objs, copper_list (2K), exp8 (2K) |
| $8000–$9FFF | 4 | header and frame loop, river generator, render, palette, random maps, play.asm (~1.6K free) |
| $A000–$BFFF | 5 | the cartridge (loaded from the SD card; esxDOS F_OPEN/F_READ, long name then RIVER_~1.ROM; checked: 8192 bytes, $BFFA = $A000) |
| $C000–$DFFF | 6 | game.asm, display.asm, sprites.asm (~350 bytes free) |
| $E000–$FFFF | 1 | variables, pix_tab (4 pages), mc_bullet/mc_missile, pf_class, line_start, line_after_draw, dsh_tables (12 pages), stack |

Page 7 is mapped at $6000 only while `load_rom` and `panel_init` run at the start; its free part ($0800 on) keeps the pattern cache. The NEX holds 16K banks 2 and 3 (pages 4–7).

Header at $8000 (for the checks, `tools/nxcheck.cpp`): `jp start`, the addresses of `line_done`, `frame_done`, `apply_done`, POKEY's counter at the first read (3 bytes), the controls (in_stick ×2, in_trig, in_console, in_key at 12–16), `tv_init` (17), `rnd_feed_on`, `rnd_feed`, `rnd_feed_reads` (18–20).

## The frame
`main_frame` (river_raid.asm): snapshot what the display shows (scroll, edge and water colours, player), controls, CAPS + 1; then `prepare`, `display` (the DLI), `build_sprites` (sprites and the Copper's list), `main_loop`, `vbi`; or during a reset (sub $B0F1 clearing memory: 13 frames NTSC, 8 PAL) only display, sprites, two pages of Layer 2 cleared and the VBI, and `finish_reset` in the last. Then `wait_frame` (raster line 208 NTSC, 220 PAL: below the scrolling line, so nothing on screen changes while it is drawn) and `apply`: Layer 2's scroll and colours, the sprites' attributes, the panel and scrolling line, the Copper's list.

## Next hardware as used
- **Layer 2** 320x256, 8 bits, stored by columns (byte x·256 + y, 32 columns per 8K page): a river line is a column-wise write of 320 bytes (`render_line`, through `pix_tab`). Vertical scroll NR $17; the river's ring of 256 rows moves one row per new line. Clip window rows 40–199. Index 0 black, 1 bank (Copper per line), 2 edge, 3 water (apply: red while a bridge flashes, black while the screen is cleared).
- **Palette writes** with NR $41: 8 bits; the 9th (blue LSB) becomes (b1 | b0). The colours are the C++ port's PAL colours (Altirra's model) through `tools/next_palette.h` (8-bit, never $E3, the global transparency). The fallback colour NR $4A is extended the same way.
- **Sprites**: pattern RAM is 64 slots of 256 bytes ($303B). The objects (player 3) have 8-bit patterns, a dot's colour index in each byte: 128 + Atari colour / 2, the sprites' palette 128–255 set once to the Atari's colours (`init_video`), 0 transparent; slots 12–61. The other players and missiles have 4-bit patterns (128 bytes; pattern p = slot p/2, bit 7 of $303B for the second half, attribute 4 bit 6 (N6) the half, bit 7 = 4-bit), a palette offset for their colour: two sets of 12 in turn (0–11, 12–23: slots 0–11); 124–127 fixed: the fuel needle and the logo. X is 9 bits and wraps round 512, which puts sprites partly off the left edge. Scale bits for double and quadruple width.
- **Copper**: mode %11 (restart each frame). WAIT h = 40 (past the 320 dots) on the line before the one to change; line L of Layer 2 is v = L − 32. MOVE NR $43/$40/$41 for palette entries, $31/$30 for the tilemap's scroll.
- **Tilemap** 40x32 with attributes, 512-tile mode (attribute bit 0 = tile bit 8), NR $6E = $21 (map at bank 5 + $2100), NR $6F = 0 (tiles at bank 5 + 0), pixel 0 transparent (NR $4C), clip rows 200–239 (NTSC) or 200–255 (PAL). Layer order USL (NR $15 = %00110011): tilemap over sprites over Layer 2; sprites over the border, clipped to their window (bit 5; X doubled): rows 40 to the panel's last, so an object's rows above the river are not shown.
- **50/60 Hz**: NR $05 bit 2, read-modify-write (the other bits are the joystick modes and the scandoubler).
- **Controls**: keyboard half-rows on port $FE; Kempston 1 at $1F, 2 at $37 ($FF there means nothing connected); Mega Drive pads: bit 7 START, bit 6 A.
- **Clock and interrupts**: 28 MHz (NR $07 = 3), set at start; only speed depends on it (the DLI model counts Atari cycles). Interrupts stay off (DI): per-line changes are the Copper's, and the frame goes live by polling the raster line (NR $1E/$1F). Line interrupts (NR $22/$23) and the sprite collision flag ($303B bit 0) are not used: the flag knows neither which sprites nor the playfield, and is set only as the beam draws, a frame too late.

## Sprites from the Atari's players and missiles
`build_sprites` in the order `Game::drawRiver` draws: player 3 from the DLI's record (`scan_p3/x/size/col` per scanline), then the plane (player 2), its bullet (missile 2), the tank (player 1), the helicopter's missile (missile 0), the shell (player 0) from player-missile memory at one position. A run is up to 16 lines at one position and size; each run is a sprite. An Atari pixel (colour clock) is two sprite pixels: a byte's 8 bits are 8 bytes of $11/$00 (`exp8`). Missiles' bits become a player's byte through `mc_bullet` (1 clock a bit) and `mc_missile` (2 clocks a bit). Lines are scanned 8 at a time (OR of 8 bytes). At most 60 sprites a frame; the most seen in the checks is 11.

**Objects' sprites**: `display` keeps each object's rows as it writes them (`ds_obj`, 8 bytes in `ds_objs`: the first row's scanline, how many rows before the river's end, the addresses of the first row's byte and colour, position, size). `build_sprites` makes a sprite of each 16 of them (`ob_list`, `ob_emit`): an 8-bit pattern with the rows in their colours, found again by its key (the two addresses and the number of rows: an object partly above the river or at its end has fewer) through a hash table (page 7: OB_BUCKETS, OB_*); a new one takes the next slot not used this frame or the last (still shown), round robin. So an object costs its attributes only, and a pattern is written once per shape, frame of animation and clipping. The objects' rows are always these, the DLI behind or not (as the C++ port draws them); nxcheck compares them with the C++ port's `drawn` every frame.

**The other players and missiles** (`pm_channel`): one sprite each, its rows where the game put it, the boxes `ds_cover_set` marks for the collisions: the shell 16 rows from shellY, the tank 11 from tankY, the plane 14 from $AA, the helicopter's missile its row missileY (from $1C), the bullet 8 rows below bulletY; the river's lines of them, none if empty; a missile's bits turned into a player's bytes (`ch_bits`). Their memory has nothing elsewhere on the river (the test build's `pc_check` counts rows outside the boxes: none), so it is not searched any more.

**Pattern cache** (the 4-bit ones): a sprite's 16 rows (its key) are hashed; a hash table per set (page 7: PC_BUCKETS) gives a pattern of that set with the same rows if there is one, else the next pattern not used this frame takes them (round robin, the old hash entry removed). Pattern RAM is cleared at the start so the cache (all zero) agrees.

**Copper list**: for each river line, the bank colour where it changes (Layer 2 entry 1), set on the line before, from the display's changes (`ds_bank_ev`). Made again only when they change (`cp_colour`: one colour all the way, as the list has it: nothing to do); then `apply` sends it all to the Copper (`cp_full`), otherwise only the scrolling line's X scroll (the list's last MOVE's value, one byte). `nxcheck` checks after every apply that the Copper's memory is the list and that the list's colours are `scan_bank`'s changes. Then the panel's part (from `copper_panel_ntsc` or `_pal`): Layer 2's colours 0–3 black on line 200 and grey from 201, tilemap Y per character row, X scroll for the scrolling line (patched by `panel_frame` with the frame's fine scroll).

## The panel and the scrolling line
Character sets built at the start where the game builds them (A0FB–A143): the OS font's pages $E000/$E100/$E300 (AltirraOS's, `src/font.inc`, made by `tools/mkfont` from the C++ port with its notice) and the cartridge's symbols ($BEEE logo lettering, $BF2E panel symbols, $BF9E player labels, $BFB6 year digits). They stay at $0600–$09FF (start_attract leaves that range). Each character is two tiles (left and right 4 colour clocks, two dots each): tiles 0–127 the panel's set, 128–255 the scrolling line's.

Map rows: the panel's three at 20, 22, 23, the scrolling line at 26; the Copper sets the tilemap's Y scroll so that they come at lines 202/211/219 and 231 (NTSC) or 206/218/226 and 243 (PAL), from `status_bar.cpp`'s layouts plus 20. The panel's first character starts 8 dots left of the screen: column 0 is its right half, column 39 empty.

The scrolling line moves 1 colour clock (2 dots) a frame: its text starts 38 − 2·fine dots left of the screen. The X scroll is s = (38 − 2·fine) & 7, the first half character H0 = (38 − 2·fine) / 8; column t shows half character H0 + t. Column 0 is seen twice: dots s..7 at the left edge (half H0) and dots 0..s−1 at the right edge (half H0 + 40), so tile 256 is made each frame from those two halves.

The panel's grey (COLBK $06) is Layer 2 from line 201 to 229 (NTSC) or 239 (PAL): its clip window reaches there (tv_setup), and the Copper makes its colours 0–3 (all a river line has) black on line 200 and grey on 201; apply makes 0 black again below the scrolling line (2 and 3 it sets every frame, 1 is the Copper list's first MOVE), and the Copper itself sets 0–3 back on line 230 (240 PAL), right after the grey, with the edge and water colours apply writes into its list (`CP_EDGE_BACK` bytes from the end; sent with the X scroll when the list is not sent whole): else a late frame, whose apply comes after the next frame's top, shows the river all grey but the bank (seen at 14 MHz). Layer 2 is under the sprites, so the fuel needle (sprite, missile 1) is over it and the characters over the needle, as PRIOR 4 has it on the Atari. It is 320 dots wide, as the river (colour clocks 20–179). The C++ port shows the river and the panel at clocks 12–179 (half clocks 24–359 of 384, `kVisibleFirst`/`kBackFirst`) and the scrolling line all 192: the Next lacks 8 clocks on the left. They cannot go into the border: no layer draws past the 320 dots, only the fallback colour (one a line, both sides), so a strip there would be a flat colour without the houses' parts, the sprites (planes, helicopters, ships) would vanish over it, and a left-only strip needs 2 Copper writes every line (about 1.5 KB of the list, rebuilt and sent every frame near bridges). Left as it is. It used to be the fallback colour, which also filled the border (the 20 dots each side that Xpeccy+, like the Next's HDMI, shows past the 320): the panel looked wider than the river. The logo is five sprites: three 16-dot parts of player 3 at quadruple width (data $FC) and two for player 2 (data $FF) one colour clock further left each row; seven colours from $B48D in sprite palette offset 5.

The scrolling line is the Atari's wide playfield, 192 colour clocks (24 mode 6 characters); the Next's 320 dots show 160 of them (20–179), so in the attract mode, while the text scrolls, 2 characters are missing on the left and about 1 on the right against the C++ port (which draws all 384 half clocks). In play the line is the logo, characters 7–11 of 25: whole. The checks compare only the 320 dots, so they do not see it. The one way to show it all: the tilemap's 80-column mode on the scrolling line's rows only (NR $6B switched by the Copper and back for the panel), 3 half dots a colour clock (576 of 640): the line's characters 3/4 as wide as the panel's, its own tiles and map row, the logo narrowed too. Not done.

The picture's shape: the C++ port draws the Atari's pixel 0.86 as wide as it is high on NTSC, 1.03 on PAL (`tv.h`, `pixelAspect`): the NTSC picture is taller. Xpeccy+ shows the Next's dots square at both rates (its options: keep the ratio or stretch to the window). A real Next at 60 Hz sends 720×480 over HDMI, which a 4:3 screen shows with dots about 0.89 as wide as high, near the Atari's NTSC; at 50 Hz 720×576, near square. So the program does nothing about it: narrowing the river (160 colour clocks into ~137 dots) would be wrong on a real screen.

## The DLI model (display.asm)
As `display.cpp`'s Beam: 114 cycles a line; at the start ANTIC takes 5 (players and missiles) + 1 (display list) or + 3 (an instruction with an address: the top row and where screen memory goes on in the other block, and the panel's first line, 190 NTSC / 194 PAL, which takes 3 and leaves 20 after the draw); the line is drawn at cycle 28, then 9 refresh and 48 screen data on a river line; STA WSYNC waits for 106.

`op n` / `opa`: an instruction of n cycles; IXH holds the cycles to the next event (signed); events due before the instruction happen first (`bm_events`: the line drawn, then the next line). Instructions with nothing the beam sees between them are one op.

What a drawn line does (`bm_draw`): if player 3 is on it, its position, size and colour into `scan_x/size/col` (only there: nothing looks elsewhere); collisions if any player or missile is there. Player 3's data is kept as the lines latch it: `scan_p3` starts as a copy of its memory, and a write to a row whose line has not started yet goes into it too (`p3_scan`). The bank colour is recorded when it changes (`rec_set`: the lines since the last change get the old value; `rec_end` fills to the river's end).

### Fast loops
Inside an object's rows (B5CB–B5E5), after the first STA WSYNC, every line is the same: the colour part starts the next line (more than the 8 cycles left), writes the road's bank colour (on a bridge) and player 3's colour before the line is drawn (they come at cycle ≤ 21, the draw at 28), then the next row's shape part draws the line (before or after player 3's row is written, which does not matter: it is latched already) and STA WSYNC ends at cycle 106 again. So `.fast` does those events in that order, and the beam's count (IXH = 32 − cycles before STA COLPM3 − ANTIC's cycles at the line's start) is only worked out where the loop is left (`.row_tail`). The same for the wait for an object's first line (B567–B573: STA WSYNC past the line's end starts the next line and holds the CPU until it is drawn). Only river lines (28–187) go this way. This took a third of the frame's work off.

The rows that cannot leave the loop (not a bridge, the line not the river's last, the counter not wrapping, a row left) go tighter still (`.tight`): their number, the least of the three limits, is worked out once and counted in IXL; the pointers stay in registers, only `bm_line`, `colour_p3`, player 3's memory and its latched row (`scan_p3`) are written, and the beam's count is left as the drawn line leaves it (106); the first row that may leave goes through `.fast_gen`, which works out the count. The wait for an object's first line keeps the slot's y in IXL (`.wait_y`): STA WSYNC leaves the count at 106 and the line drawn, so only the line and the counter change. Between instructions the beam sees (a register written, a collision read, WSYNC, HITCLR, player 3's memory), the cycles of the others (branches, INX, the game's own memory) go with the next one that it sees: `opk k, n` (k cycles, then an instruction of n) and `opc n, k` (C + k first); the events of those cycles happen before it all the same. Together these took the DLI model from ~191 000 ticks a frame to ~134 000.

### Collisions
Only what the DLI reads (B5E8–B664, B6BC on): P3PF (edge), P1PF (edge), P2PF (bank), M0PF and M2PF (bank, edge); M2PL (player 3), P3PL (player 0), P2PL (players 0 and 3), M0PL (player 2). Per sprite on the line, the playfield's colours under it (`pf_under`): its bits doubled (2 bits a colour clock), 1, 2 or 4 bytes q, each shifted by the clock within the first screen byte is 3 bytes from `dsh_tables` (12 pages: for shift s, byte k), ORed at byte 2i; ANDed with the screen bytes; `pf_class` gives the colours of a byte (bits 1 bank, 2 edge, 4 water), accumulated in the other register set. Unrolled for normal, double and quadruple width when all bytes are on the line; byte by byte near the edges. Nothing to do if all bytes under it are water ($FF: water is never read), nor for player 3 once P3PF's edge bit is set (it stays until HITCLR). Two sprites touch: their spans (position to position + width) must meet, then each colour clock of one (over the playfield: 32–223) is looked up in the other's bits.

A line's screen memory: screen memory is a ring of 160 lines (80 in each block: +48, $2Fxx → $30xx, $3Fxx → $20xx); `ring_lo/hi` (built once) give each slot's address, and the river's top slot is found once per frame from $3F04.


### Without the cycles (display_simple.asm, the default)
`display` follows the C++ port's `Game::displaySimple` (its docs/DLI_REMOVAL.md): the DLI's loop with X only (the line drawn while X = c is c - 69 + `ds_slip`). It is a schedule: which rows each object shows (from max(X, its Y), to the river's end), where each read and HITCLR comes, the cycles; player 3's memory and registers by scanline are not written (nothing but GTIA reads them): each object's rows go into `ds_objs` (`ds_obj`), drawn from there (build_sprites) and checked by nxcheck against the C++ port's `drawn`. The rows themselves are gone over only for a bridge (its road colours) and for P3PF (only its edge is read; until it is set; only for the kinds whose bit moveObjects reads: helicopters, balloons, ships, $08-$0D, `ds_edge_kind`, the others' read as 0 as in the C++ port) against the line's runs of edge pixels: first the row's first and last dots (`edge_lo/hi`, by the row's byte, made at the start; doubled for a ship) plus X against the runs, and only for a run between them the dots themselves through the size's variant (`pf_v1/2/4`, set up once an object; the rows have gaps). A bridge's road colours are kept as a list (`ds_bank_ev`) filled into `scan_bank` at the end, only when they change (`ds_bank_last`). The collisions come without the scanlines' registers (`display_hits.asm`, the C++ port's displaySimple): the other sprites' rows are where the game put them (`dh_desc`: the shell 16 rows from shellY, the tank 11 from tankY, the plane 14 from $AA, the missile the row missileY, the bullet 8 rows below bulletY), so at the frame's start `dh_lists` works out the scanlines of each collision the DLI reads (P1PF the tank and the edge, P2PF the plane and the bank, M0PF and M2PF the missile and the bullet and either, through `pf_*`; P2PL the plane and the shell, M0PL the missile and the plane, through collide's `.add` and `.pair`); a read counts one if its scanline is from the last HITCLR's (`ds_cleared`) to its own (`dh_seen`). An object's collisions with the bullet (M2PL, to the scanline before its last row, a bridge's included), the shell (P3PL) and the plane (P2PL) are worked out at its reads against its entry in `ds_objs` (`dh_obj`: first whether their clocks meet at all, the object's 8, 16 or 32 from its X and the sprite's 8, 4 or 2 from its), the edge in its rows' loop (`dh_edge` for rows written late). The beam's per-line collisions (`bm_draw`, collide's body) are left to the cycle model (`-DBEAM`). The playfield's runs (`span_line`) come from the line without its decoration (`plain_line`: draw_line keeps where it drew the houses and roads, `dl_deco`), as the C++ port's bankRuns: 2-8 boundaries a line. The rules with cycles: M0PF sees the line too when 28 cycles (30 after an M0PL hit) plus the line's start reach 36; HITCLR clears the next line too when 23 cycles + 2 a hit stored plus its start reach 36; a stretch between WSYNCs longer than 28 + the line's cycles after its draw - its start (B5B0-B5D1: 49/50; a bridge's last row: 46/48; B5F3-B61F: 44/43 + 2 a hit) puts the DLI a line behind (`ds_chunk`). Then (0-10 times in 100 000 frames) the original shows last frame's rows where the late ones go; the new ones are drawn here, as the C++ port does. The cycle model (`display` above, `-DBEAM`) is kept for comparison.

## POKEY's RANDOM
`random_read` returns bits 16–9 of `rnd_state`, the counter at the game logic's read (scanline 192 cycle 13 NTSC, 191 cycle 24 PAL). `random_step` (each VBI) moves it one frame on: 262·114 or 312·114 steps, a linear map over GF(2) as 17 columns of 3 bytes (`src/random.inc`, `tools/mkrandom`), applied 4 bits at a time: `rnd_tables` (end of `tv_setup`) XORs the columns of every value of each nibble of bits 0–15 into `rnd_tab` (256 bytes, page 1) and keeps bit 16's column (`rnd_col16`); `random_step` is 4 lookups and XORs, ~560 ticks (bit by bit it was ~2 300). The C++ port instead keeps the counter as its position in the 131 071-state cycle (a jump is one addition) with ~1 MB of tables; on the Next that would be 128 KB (the read byte only) and ~0.3 s to build at start for ~450 ticks more saved: not worth it. The start: `rnd_init` mixed with R (release) or `pokeyFirstRead(seed)` (checks). Test builds can take RANDOM from the checks instead (`rnd_feed`).

## Sound (src/sound.asm, src/sound_pulses.asm)
Pure tones on the AY (set up by `src/sound_ay.asm` in page 7; what runs every frame, `ay_frame`, `ay_out`, `ay_quiet`, in `src/sound_ay_run.asm`, page 6: see the crackle below): POKEY's channels 1, 3, 4 playing a pure tone (AUDC bits 7-5 101 or 111, bit 4 clear, volume ≠ 0: the start beep, low fuel, refuelling, tank full, firing, a bonus life, the shell's whistle) go to the first AY's A, B, C and are skipped by the DAC's loop (`ay_mask`). Period N = (AUDF + 1) × 3.454 PAL / 3.422 NTSC (1.75 MHz / 16 against the Atari's clock / 28; `mul d,e`), the volume through `ay_vol` (the nearest on the Next's YM table to the DAC's 32 v in the mix; from v = 8, the tones' usual volume, the table's top, 255). The AY gets the registers of 2 frames ago (`ay_q`): the DAC's samples are about that far ahead. TurboSound on (NR $08 bit 1), the first AY mono (NR $09 bit 5), mixer $38. nxcheck checks the AY's registers against the C++ port's, 2 frames back. Gain in time: little (the engine is noise, always on the DAC; clearing and the running sum stay): bridge 50 and on, PAL, the sound ~25 200 ticks a frame against ~26 700; but the tones no longer depend on the DAC's samples, so they do not crackle when the sound gives way.

`sound_driver` (VBI, B2A5–B3D8, `Game::soundDriver` line for line) sets `pokey_audf`/`pokey_audc`; its RANDOM for a noise's pitch is the counter at the game logic's read (`sound_random`, not `random_read`, which the checks count). nxcheck compares the registers with the C++ port's every frame, except a noise's pitch (RANDOM read at another moment) and what stays of it.

`pokey_frame` (after the VBI, in both kinds of frame) plays them. The zxnDMA sends a ring of 1024 bytes ($7C00, page 12) to the DAC (port $DF, DACs on with NR $08 bit 3) round and round: burst mode, prescaler 55 (875 kHz / 55 = 15 909 bytes a second), auto restart; its port A address is read back every frame (read mask $18, $A7; it reads $8000 at a round's end, so it is put back in the ring). A sample is 4 POKEY ticks (28 cycles each); the DMA's rate is 0.5% above POKEY's.

How many samples: up to 760 ahead of the DMA (`SND_LEAD`, 2.4 frames, 48 ms), as many as the time left before `wait_line` allows (8 a line past 16 lines; past `wait_line` the work, which starts there, has ended before the frame's last line: as many as allowed. It used to count as a late frame (none): right while the work always ran past the frame's end, wrong once it got faster: on PAL about 1 frame in 20 then made too few, the DMA passed them and played the held level (a crackle, heard in the explosions); now none in 10 000 (test builds count it: `snd_passed`)), but enough for 200 ahead (`SND_MIN_LEAD`), 700 at most (`SND_CAP`). So a busy frame leaves samples to the next ones. Past the new samples, when they are less than 600 ahead, up to 400 samples (`SND_HOLD`) of the last level: if the DMA gets there before the next frame's samples it plays that (a short flat stretch), not what the ring had a round ago (that quacked). If the DMA has passed them, they go on from where it is, as many as the time allows. Under too much work the sound gives way, not the game: at bridge 50 and on, flying without crashing (`NXSOLO`), about 7% of the samples are held on PAL; with 420 at least (1.3 frames) instead of 200, 1 frame in 65 was late instead of 1 in 235.

The ring's stretch is cleared (pushes, one more sample than the frame's), each channel adds + or − its volume × 8 where its output turns, and a running sum (`snd_sum`) from the frame's first level (the channels' outputs as they are) makes the levels (0–240). The gain was × 4 (levels 0–120 in the game, half the DAC's range, quieter than the C++ port); the channels on the DAC add up to 30 at most in the game (measured: 5.4 million samples, bot 3, 20 000 frames), so × 8 fills the range (240). × 8 keeps the DAC's noise and the AY's tones in the C++ port's balance: v = 8, the tones' usual volume, is already the AY's top (255), as 8 × 32 = 256 is; a gain of 12 a frame (8 in loud frames) was tried and dropped: the tones fell 1.5 times behind and the gain jumped between frames. Against the C++ port the Next is about half as loud whatever the program does (one DAC a side at full swing is 255 × 64 = 16 320 in the core's mix, 80% of that at Xpeccy+'s default DAC volume; PokeySound gives 800 a volume unit): DAC and PSG at 100 in Xpeccy+ make up a quarter of it. The gain is fixed: past 31 the levels would pass 255 and wrap (the + and − are added modulo 256), but the game never gets there. A turn some ticks into its sample is split between that sample and the next (`pk_on`, `pk_off`: the volume × 0–3 of 4 before it, `snd_tables` + $90): an average over the sample, as POKEY's output is; with whole samples the half periods of the start beep (65 ticks) went 16-16-16-17 samples and it buzzed at half its pitch. A channel with volume 0 is skipped; volume only (AUDC bit 4) and AUDF ≤ 4 (5 ticks or less: above what the samples can show) are a constant level (all or half its volume). The others go from pulse to pulse: the first pulse's sample (`CH_D`, `CH_F` ticks × 64), K = (ticks − 1 − first) / (AUDF + 1) + 1 pulses this frame (a division; B and `pk_kh` rounds of 256), then a loop per kind: a tone (AUDC bits 7-5 = 101, 111) turns at every pulse; noise (100) takes the 17-bit counter's next bit (`poly17.bin`, 131071 bits at the ticks, mapped at $0000-$3FFF while it runs: the bits in turn, not 28 × (AUDF + 1) apart: the same spectrum, measured, and cheaper); the 4-bit counter let through by the 5-bit one (010, the helicopter's missile) its own loop; the rest through handlers. The 4-bit and 5-bit counters step by (AUDF + 1) mod 15 and mod 31 (`snd_mod15`, `snd_mod31`, made by sound_init; `poly4`, `poly5`: tick k sees bit 28k, `tools/mkpoly`).

Cost (bot 1, 10 000 frames): ~25 000 ticks a frame PAL (321 samples), ~21 000 NTSC (267); up to ~60 000 (the engine, an explosion, firing and a missile at once). `snd_sum` ~8 600, noise ~4 000, clearing ~2 800, the channels' set-up ~2 900, the turns ~3 900, the driver ~800.

Mistakes found: the part of a turn past the frame's end carried into the next frame was counted twice (the next frame starts from the outputs), a level below 0 wrapped to nearly full (loud clicks); the DMA's address read as $8000 at a round's end, used as the ring's place after an underrun, made the clearing push 8K of zeros under $8000 (page 12: the DLI's lines); a first version adding each channel's runs of samples and calling per run cost ~31 000 on average and up to ~147 000; with no cap, and with samples forced after an underrun, a late frame made the next one late too.

The crackle that stayed after the sample count was fixed (heard on Xpeccy+, NTSC, in flight, firing, explosions): the DAC played a 0 for 1–2 samples about once a frame. pokey_frame mapped page 7 at $6000-$7FFF (`nextreg $53,INIT_PAGE`) to call `ay_frame`, but the DAC's ring is at $7C00 in page 12, and the zxnDMA reads memory through the same MMU: while the AY code ran, the DMA sent page 7's bytes (zeros there). The ring as written was right, so `-wav` and `snd_passed` showed nothing; it showed with the DAC's port writes traced in the core (a hook in `nx_dac_out`, not kept): 1029 wrong samples of 653 000, all at PCs in `ay_frame`/`ay_out`. Now the per-frame AY code is in page 6 and $6000-$7FFF stays page 12 whenever the DMA runs (sound_init also enables the DMA, `$87`, only once page 12 is mapped back). The trace after: 0 wrong samples, the writes 1 766–1 773 core ticks apart. Rule: nothing may map another page at $6000-$7FFF while the sound plays.

nxcheck: `-wav FILE` writes the samples the program made, `-wavcpp FILE` the C++ port's PokeySound at the same rate from its registers; it prints the samples per frame and `pokey_frame`'s time. `NXSND=N` prints the registers, channel 1's state and samples near frame N; `NXSNDCHK=1` every frame whose samples go above what its DAC channels' volumes add up to, at the frame's gain (a level that wrapped below 0 shows as ~250); `NXCPPNOTONE=1` leaves the pure tones out of `-wavcpp`, as the program's DAC does (to compare loudness: the two are the same, RMS 2.27 against 2.26 volume units); `NXSLOW=T` the frames whose work is over T ticks (with the lines left and samples made) and the late ones; `NXGAME=n` has the bot play game n (7: from bridge 50). The busy scenes of the later bridges, which the bot does not reach otherwise: `NXBRIDGE=n` starts every game at bridge n on both sides (the C++ port's `RiverGen::setRiver`; the program's starts patched into the ROM's tables at $B494/$B4A4/$B4A8 and the hundreds into `start_bridges_hi`, test builds); `NXSPEED=n` sets the CPU's speed (NR $07: 2 = 14 MHz) by patching `start`; `NXBORDER=1` turns T's border on; `NXGHOST=1` makes the plane unable to crash and keeps the fuel full on both sides after the display (the program's `test_ghost`, as the C++ port's display_bench), so they are compared too (`NXSOLO`, which made only the program's plane unable to crash and compared nothing, is gone).

Loudness. The program's levels equal the C++ port's (RMS 2.27 against 2.26 volume units with the pure tones left out of both, `NXCPPNOTONE`). The Next is quieter in the emulator because of the mix, not the sound: one DAC a side (port $DF feeds DAC A, left, and D, right; B and C stay at their idle $80), 4 × its level in the Next's 13-bit mix, 16 times that in Xpeccy+'s output (`NX_GAIN`): a level of 240 is 15 360 against the C++ port's 30 × 800 = 24 000 for the same sound; and Xpeccy+'s DAC and PSG volumes are 80 by default (its Options, Sound: Master, Beeper, Tape, PSG, DAC, General Sound, SAA1099), the DAC carrying the noise, the PSG the AY's tones. With DAC and PSG at 100 it is about 0.8 of the C++ port's. A louder DAC would leave the AY's tones behind (already at the YM table's top), so the gain stays 8, fixed.

Mono. POKEY has one output, River Raid one POKEY, the C++ port is mono. The DAC's noise cannot be stereo here: the DMA sends one stream to one port, and $DF puts the same byte in the left and the right DAC. The AY's tones could be spread (the first AY in ABC stereo instead of mono, NR $09 bit 5) at no cost; not done, as the original is mono.

## Speed

## The checks (tools/nxcheck.cpp)
Xpeccy+'s ZX Spectrum Next core as a library (libxpeccy, MIT), headless: the SRAM loaded with the test pages (4, 6, 7) and the ROM (page 5), a `jp $8000` at 0, run instruction by instruction. Hooks: `frame_done` (a frame worked out), `apply_done` (live).
- **Against the C++ port** (default): `rr::Game::frame` beside it with the same POKEY counter and the same controls from a made-up player (Bot: waits, selects, starts, steers to the water's middle, dodges, refuels, fires, pauses). After every frame: the generator (`RiverGen::diffWithRam`), the game's fields (game_ram.cpp's list, the scrolling line too), high scores, panel, player-missile memory, screen lines, the DLI's record per line (player 3's x/size/colour only where it is). At the end the picture: the core's frame buffer against `drawRiver` + `drawStatusBar` in the Next's colours, Layer 2 rows 40–255. Before taking it, the program is stopped (JR $ at apply_done) so the next frame's apply cannot come in (at 60 Hz it did). `-pal`/`-ntsc`, `-switch N` (CAPS + 1 before frame N, both restart), `-bot N`, `-seed N`, `-attract`.
- **Against the original** (`-oracle DIR`, `make check-original`): rr_oracle's runs (ram.bin, random.log, frames.csv) from the attract mode's start (frame 38 / 25), the original's input and its game logic's RANDOM values (reads on scanlines < 240; the VBI's are sound); after every frame the program's RAM through `Game::loadFromRam` + `diffWithRam` against the original's, with a display list made as the original's (the program keeps none), half-done snapshots (the original not waiting at AE99–AE9E) and reset frames not compared, and after a difference the original's RAM copied into the program's.
- **Profiling**: `NXHISTALL=file` (all frames' work), `NXHIST=file` (the frame after FRAMES), `NXPROF=addr,...`; `tools/prof.py build/test.sym file` per routine.

## Things learned the hard way
- sjasmplus: a `name = value` (DEFL) is a label and starts a new scope for local `.labels`; use local names or unroll. `PM_X << 8 | n` with a 16-bit address loses the page: write `high PM_X << 8 | n`. Out-of-range `jr` after growing code: `jp`.
- Xpeccy+ in non-firmware mode: palettes are all zero after reset, so the program sets every entry it uses; `comp_power_on` breaks the setup.
- At 60 Hz the core's picture has no top border rows before Layer 2 row 0 (at 50 Hz 24).
- The display list is not kept by the program: the river is drawn from Layer 2, the DLI's lines from the ring; only $3F04 (top line) and $3FB3 (the scrolling line's text) are kept, as the C++ port's state has them.
- The zxnDMA reads memory through the MMU, as the CPU does: mapping another page over the DAC's ring while the DMA runs makes it play that page (the crackle of 1–2 zero samples a frame, from `nextreg $53` around the AY code). The ring as written and `snd_passed` cannot see it; a trace of the DAC's port writes in the core can (a function pointer called from `nx_dac_out` in zxnext_snd.c, logging the edge, the value and the PC; it was not kept, as it changes the pinned Xpeccy+).
- A self-modified gain must be checked byte by byte: a variant that left one `add a,a` in place of a `nop` doubled the levels and wrapped them (NXSNDCHK caught it).
- Before trusting a check, make sure the assembly succeeded: a failed build leaves the old pages, and nxcheck runs those.
